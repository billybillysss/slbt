# Concepts and boundaries

## A transformation semantic layer

In slbt, a semantic definition combines **how a value is derived** with **what
it means**: expressions, upstream relations, descriptions, types, tests,
constraints, ownership and model configuration. Layer/domain classifications
organize those definitions. The semantic layer is built, not hidden behind a
generated query you cannot review.

This is not a metrics-serving API, a natural-language query engine, or dbt's
Semantic Layer/MetricFlow. slbt does not currently provide a metric query service,
an LLM client or an autonomous agent. AI assistance works through ordinary files
and external tools; see the [review workflow](guides/ai-assisted-workflow.md).

## One canonical source, multiple interfaces

| Artifact | Ownership and role |
| --- | --- |
| YAML models, sources, classifications, project configuration; SQL macros | Canonical inputs, version-controlled and reviewed. |
| Generated dbt SQL, properties and snapshots | Build outputs. Regenerate rather than hand-edit. |
| dbt documentation | Generated by dbt from exported properties and dbt's own catalog/manifest. |
| Resolved JSON | Read-only semantic export, useful as AI context or integration input. Not a replacement for canonical YAML. |
| Excel/CSV catalog | Editable collaboration surface. Validated import proposes canonical changes. |
| Database relations and test results | Owned by dbt and the selected adapter/engine, not slbt. |

`steps` are model-local transformations, not separately materialized dbt models.
`output` defines the model's final ordered columns. A logical `ref` points at a
model; `source` points at a registered physical binding. Dependencies are inferred
from logic, rather than maintained as a second handwritten list.

## Validation is not execution

slbt validates definitions and SQL offline, expands supported macros, renders
ordinary dbt files and simplifies logical SQL. It cannot prove a business rule is
right, check live data quality, discover unknown warehouse schemas or guarantee
physical query performance. Descriptions and tests still need human review.

Runtime macros may depend on adapter introspection and only resolve during dbt
execution. Validation/export can retain them, inspection rejects them, and
optimization skips affected models unchanged with a reason.

## Make AI-generated logic inspectable

An external assistant can read scoped JSON and propose canonical YAML. Review the
YAML diff, inspect expanded SQL, preview optimization, and execute dbt tests before
accepting it. Keeping definitions and generated SQL visible removes an opaque
handoff; it does not remove the need for domain expertise or data testing.
